### B-01 ★. 기존에는 FastAPI와 Celery Worker를 WSL에서 직접 실행했지만, 최종 프로젝트에서는 Redis·PostgreSQL과 함께 Docker 컨테이너로 실행하도록 변경했습니다. 이렇게 변경한 이유와 장점은 무엇인가요?


**모범답변** 

기존에는 Redis와 PostgreSQL만 Docker로 실행하고, FastAPI와 Celery Worker는 WSL의 Python 가상환경에서 각각 실행했습니다.

하지만 개발 환경마다 Python 버전이나 설치된 라이브러리가 달라 오류가 발생할 수 있고, 서비스를 개별적으로 실행하고 관리해야 하는 불편함이 있었습니다.

그래서 최종 프로젝트에서는 FastAPI, Celery Worker, Redis, PostgreSQL을 각각 Docker 컨테이너로 구성했습니다.

Docker Compose를 사용하면 `docker compose up -d --build` 명령으로 네 서비스를 함께 실행할 수 있으며, 개발 환경을 일관되게 유지하고 다른 PC나 서버에도 동일한 구성을 배포하기 쉬워집니다.

또한 서비스별로 컨테이너를 분리하므로 로그 확인, 재시작, 장애 분석이 편리하고, FastAPI와 Celery Worker가 동일한 애플리케이션 코드를 사용하면서 각자의 역할을 수행할 수 있습니다.

### B-05 ★. 비동기식(Async) 웹 화면에서 AI 이미지 분석 버튼을 누르면 어떤 과정을 거쳐 결과가 화면에 표시되나요? 관련 파일과 각 서비스의 역할을 설명해 주세요.

비동기식 웹 화면인 `templates/async.html`에서 이미지 분석 버튼을 누르면 JavaScript가 `FormData`에 이미지를 담아 FastAPI의 `POST /api/async/classify/`로 전송합니다.

`ai/router_async.py`는 이미지를 서버에 저장하고 PostgreSQL에 작업 상태를 `queued`로 기록한 다음, Celery에 작업을 요청하고 작업 ID를 먼저 반환합니다.

Celery Worker는 Redis를 작업 메시지 브로커로 사용하여 요청받은 작업을 실행합니다. `ai/tasks.py`에서 저장된 이미지를 읽고 ResNet18 모델로 분석한 후 결과와 작업 상태를 PostgreSQL에 저장합니다.

브라우저는 작업 ID를 이용해 `GET /api/async/jobs/{job_id}/`를 주기적으로 호출하며, 작업이 완료되면 저장된 분석 결과를 화면에 표시합니다.

비동기식 전체 파이프라인

```
[templates/async.html]
이미지 분석 버튼 클릭
          ↓
[ai/router_async.py]
FastAPI 이미지 수신
          ↓
이미지 파일 저장
PostgreSQL 작업 등록 (queued)
          ↓
[ai/celery_app.py]
Redis를 통한 Celery 작업 전달
          ↓
[ai/tasks.py]
Celery Worker 작업 실행
          ↓
[ai/cache_service.py]
Redis 분석 결과 캐시 확인
          ↓
캐시 MISS라면 ResNet18 추론
          ↓
PostgreSQL에 결과 및 상태 저장 (done)
          ↓
[templates/async.html]
작업 ID로 상태 주기적 조회
          ↓
분석 결과 화면 출력
```

### B-9 ★-1. Redis에서 Cache HIT(캐시 히트)란 무엇인가요?

모범답변

Cache HIT는 요청한 데이터가 Redis에 이미 저장되어 있는 상태를 의미합니다. 이번 프로젝트에서는 동일한 이미지의 분석 결과가 저장되어 있으면 ResNet18을 다시 실행하지 않고 기존 결과를 반환합니다.

### B-10 ★-2. Redis에서 Cache MISS(캐시 미스)란 무엇인가요?



모범답변

Cache MISS는 요청한 데이터가 Redis에 없는 상태를 의미합니다. 이 경우 ResNet18 모델로 이미지를 분석하고, 분석 결과를 Redis에 600초(10분) 동안 저장한 뒤 반환합니다.

### B-11 ★-3. 이번 프로젝트에서 Redis 캐시를 사용하는 이유는 무엇인가요?



모범답변

동일한 이미지에 대해 ResNet18 추론을 반복하지 않기 위해서입니다. 캐시에 결과가 있으면 기존 결과를 재사용하므로 응답 시간을 단축하고 서버의 연산 부담을 줄일 수 있습니다.

---
### B-12 ★-4. Redis에 저장된 캐시가 600초 후 만료되면 어떻게 처리되나요?

모범답변

캐시가 만료되면 저장된 결과가 없어지므로 다음 요청은 Cache MISS로 처리됩니다. ResNet18이 이미지를 다시 분석하고 새로운 결과를 Redis에 저장합니다.

### B-13 ★-5. Cache HIT가 발생했을 때 `inference_ms=None`으로 반환하는 이유는 무엇인가요?

모범답변

Cache HIT에서는 ResNet18 모델을 다시 실행하지 않기 때문입니다. `inference_ms=None`은 추론 시간이 0ms라는 의미가 아니라, 이번 요청에서는 모델 추론을 수행하지 않았다는 의미입니다.

### B-23. `DATABASE_URL`, `REDIS_CACHE_URL`, `CELERY_BROKER_URL`은 코드 어디에서 사용하나요?

**모범답변** `ai/config.py`에서 `.env`를 읽어 설정값을 공통 제공하고, `ai/database.py`에서 DB URL을, `ai/cache_service.py`에서 캐시 URL을, `ai/celery_app.py`에서 브로커 URL을 사용합니다. 교재 기준 WSL 앱은 `127.0.0.1`로 Docker 공개 포트에 접속하고 DBeaver도 같은 PostgreSQL 호스트 포트를 사용합니다.

### B-24 ★. 동기·비동기의 성능을 비교할 때 어떤 세 가지 시간을 분리해야 하나요?


**모범답변** 

동기 HTTP 응답시간은 분류 결과를 받은 시점까지이고, 비동기 HTTP 응답시간은 작업 접수(`202`)까지입니다. 비동기 최종 완료시간은 Worker 처리와 상태조회까지 포함하며, `inference_ms`는 실제 모델 추론시간입니다. 같은 모델·이미지·캐시 상태·워밍업 조건으로 여러 번 측정해야 공정합니다.

**추가 확인** 접수시간이 짧다고 추론속도도 빨라졌다고 말하지 않는가?
