## 3분 대본

### 1. 무엇을 만들었나 (30초)

- 콩잎 사진을 세 가지로 분류합니다. 반점병, 녹병, 정상.
- ResNet-18 사전학습 모델의 출력층을 1,000개에서 3개로 바꿔 학습했습니다.
- 이 모델을 두 가지 방식으로 서비스했습니다.
  - 동기: 요청 안에서 바로 분류해서 돌려줍니다.
  - 비동기: 작업번호를 먼저 주고, Celery Worker가 따로 처리합니다.
- Redis는 캐시와 작업 큐, PostgreSQL은 작업 기록 저장에 썼습니다.

### 2. 성능과 개선 (1분) ← 제일 중요

- 필수 기준선인 Head-only 학습은 검증 정확도 **0.77**이었습니다.
- 코드는 고치지 않고 실행 옵션만 바꿔 두 가지를 더 해봤습니다.
  - Epoch 10번: **0.89**
  - 전체 미세조정, 낮은 학습률 5e-5: **0.985**
- 모델은 검증 데이터로만 골랐고, 고른 기록을 먼저 커밋한 뒤 테스트를 딱 한 번 봤습니다.
- 테스트 정확도는 **0.72 → 0.98** (128장 중 125장), **25.78%p** 올랐습니다.
- 녹병을 놓치는 문제가 컸는데, 녹병 재현율이 0.64 → 0.96이 됐습니다.
- 교과 9의 OpenCV 규칙도 실험했습니다.
  - HSV로 병반 면적비를 쟀는데, 정상과 병든 잎 차이가 작아서 효과가 없었습니다.
  - 대신 모델 확신도가 0.9 미만이면 "확인 필요"로 넘기는 규칙은 효과가 있었습니다.
  - 테스트에서 14%를 사람에게 넘기고, 나머지는 99.1% 정확도로 자동 처리했습니다.

### 3. 서비스 성능 (40초)

- 같은 사진으로 조건마다 5번 재고 중앙값을 냈습니다.
- 동기 첫 요청 **22ms**, 같은 사진 다시 보내면 캐시로 **1.4ms**.
- 캐시일 때 추론시간이 null인 건 0초가 아니라 추론을 안 했다는 뜻입니다.
- 비동기는 접수 응답이 **10.6ms**로 빨리 오지만, 최종 결과 확인은 **118ms**로 더 늦었습니다.
- 0.1초마다 상태를 조회하기 때문이고, 모델이 빨라진 게 아니라 접수와 추론을 나눈 효과입니다.

### 4. 검증과 한계 (30초)

- 기능 테스트 18개를 실제로 돌려 전부 통과했습니다.
  - Worker를 끄면 작업이 대기 상태로 남았다가, 다시 켜면 처리됩니다.
  - Redis를 끄면 동기는 계속 동작하고, 비동기는 503과 실패 기록이 남습니다.
- 한계: 학습을 실험마다 한 번씩만 했고, 테스트가 128장이라 한 장이 0.78%p입니다. 동시 요청 부하 시험은 안 했습니다.

## 시연 순서

1. 동기 화면에 사진 올리기 → 결과, `cache_hit: false`
2. 비동기 화면에 다른 사진 올리기 → 202, 작업번호
3. 자동 조회 → `done`, Worker 터미널에 `succeeded`
4. DB 조회 → 방금 작업 행 확인
5. 1번 사진을 동기로 한 번 더 → `cache_hit: true`, `inference_ms: null`
6. 보고서: 01번 개선 실험 표, 06번 성능 그래프

화면 주소

- 동기: http://127.0.0.1:8000/vision/sync/
- 비동기: http://127.0.0.1:8000/vision/async/
- API 문서: http://127.0.0.1:8000/docs

## 예상 질문 → 짧은 답

### 모델

**Head-only랑 Full Fine-tuning 차이?**
Head-only는 기존 특징 추출부를 고정하고 마지막 분류층만 학습. Full은 전체를 같이 조정. 콩잎 반점 같은 세밀한 특징은 Full이 훨씬 잘 잡았습니다.

**Full은 왜 학습률을 낮췄어요?**
사전학습된 가중치를 크게 흔들면 이미 배운 걸 망가뜨려서, 작게(5e-5) 조금씩 바꿨습니다.

**과적합 아닌가요?**
학습 1.0, 검증 0.985, 테스트 0.977로 차이가 작습니다. 매 Epoch 검증해서 제일 좋은 Epoch을 저장했습니다.

**테스트로 모델 고른 거 아니에요?**
아닙니다. 검증 데이터로 고르고 그 기록을 먼저 커밋한 다음 테스트를 봤습니다. 테스트 실행 기록도 로그로 남깁니다.

**검증보다 테스트가 낮은 이유?**
테스트가 128장이라 한 장 차이가 0.78%p입니다. 표본이 작아서 생기는 차이입니다.

**아직 틀리는 건?**
테스트 3장 모두 녹병입니다. 초기 녹병 반점이 작고 옅어서 반점병이나 정상과 헷갈립니다.

**제공 코드 고쳤어요?**
학습·서비스 코드는 그대로입니다. 평가·측정·캡처·규칙 실험 스크립트만 따로 추가했습니다.

**%p는 뭐예요?**
0.72에서 0.98로 오른 건 25.78%p 상승입니다. 퍼센트 비율로 몇 % 올랐다는 것과 다릅니다.

### 서비스

**202는 무슨 뜻?**
"접수됐다"입니다. 끝난 게 아니고, 작업번호로 조회해서 done을 확인해야 합니다.

**비동기가 왜 더 느려요?**
0.1초마다 상태를 확인해서 그렇습니다. Worker가 실제 처리한 시간은 30~45ms입니다.

**그럼 비동기는 왜 써요?**
추론이 길거나 요청이 몰릴 때 웹 서버가 기다리지 않게 하려고요. 이번엔 추론이 짧아서 동기가 빨랐고, 부하 시험은 안 했습니다.

**Redis를 왜 세 개로 나눴어요?**
1번은 결과 캐시, 2번은 작업 큐, 3번은 Celery 결과 저장입니다.

**캐시 키는 어떻게?**
모델 경로 해시 + 사진 파일의 SHA-256. 10분(600초) 유지. 모델을 바꾸면 키가 달라져서 예전 결과를 안 씁니다.

**캐시인데 추론시간이 null?**
추론을 안 했다는 뜻입니다. 0ms로 쓰면 아주 빠른 추론처럼 보이니까 null로 둡니다.

**Redis가 죽으면?**
동기는 캐시 없이 추론해서 정상 응답. 비동기는 큐에 못 넣어서 503, DB에 실패로 남습니다. Redis를 다시 켜면 자동으로 다시 연결됩니다.

**Worker가 죽으면?**
작업이 대기 상태로 큐에 남고, Worker를 다시 켜면 처리됩니다.

**왜 GPU 말고 CPU로 추론?**
제공 코드가 CPU로 돌게 되어 있습니다. GPU는 학습할 때만 썼습니다.

**첫 요청이 왜 느려요?**
FastAPI와 Worker가 각자 첫 요청 때 모델을 메모리에 올려서 3~4초 걸립니다. 성능 비교에서는 뺐습니다.

**왜 FastAPI는 Docker에 안 넣었어요?**
평가 가이드 구조가 "Docker는 Redis·PostgreSQL만, FastAPI·Celery는 가상환경"이라서요. 처음엔 다 Docker로 했다가 가이드대로 다시 측정했습니다.

### OpenCV 실험

**HSV가 왜 안 됐어요?**
녹병 초기 반점이 작고 연두색이라 잎 색에 섞이고, 반대로 흙이나 그림자가 잎 가장자리에서 병반으로 잡혔습니다.

**"확인 필요"는 결과를 바꿔요?**
아니요. 라벨은 그대로 두고, 사람이 봐야 할 사진만 표시합니다. 모델 정확도와 규칙 성능을 따로 적었습니다.

**기준값은 어떻게 정했어요?**
면적비는 학습 데이터, 점수 0.9는 검증 데이터로 정하고 커밋한 뒤 테스트에 한 번 적용했습니다.

**다음에 한다면?**
잎만 잘라내서 배경 영향 줄이기, Grad-CAM으로 녹병 오류 때 모델이 어디를 봤는지 확인, 여러 번 학습해서 편차 확인.

### 진행하며 고친 것 (물으면)

- 처음에 다른 프로젝트 가상환경으로 학습 → 전용 가상환경 만들어서 다시 학습·측정
- 처음 시연에 테스트 사진 사용 → 검증 사진으로 바꾸고, 테스트는 마지막 한 번만
- `pytest`가 모듈을 못 찾음 → `python -m pytest`로 실행해서 4개 통과
