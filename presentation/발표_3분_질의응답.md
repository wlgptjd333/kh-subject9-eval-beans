## 1. 3분 설명 대본

**① 무엇을 만들었나 (30초)**
> microsoft/resnet-18의 1,000클래스 출력층을 콩잎 3클래스로 바꿔 학습했고, 이 모델을 두 가지 방식으로 서비스했습니다. 동기 API는 요청 안에서 바로 분류해 돌려주고, 비동기 API는 202와 작업번호를 먼저 주고 Celery Worker가 처리합니다. Redis는 캐시·작업 큐로, PostgreSQL은 작업 이력 저장에 썼습니다. FastAPI와 Celery는 WSL의 프로젝트 전용 가상환경에서, Redis·PostgreSQL만 Docker로 띄웠습니다.

**② 모델 성능과 개선 (60초)** — 핵심
> 필수 기준선인 Head-only 학습(E0)은 Validation 0.7669였고, 특히 녹병을 정상으로 놓치는 오류가 많았습니다. 제공 코드는 고치지 않고 실행 옵션만 바꿔 두 가지를 실험했습니다. Epoch을 10으로 늘린 E1은 0.8947, Backbone까지 낮은 학습률 5e-5로 전체 미세조정한 E2는 0.9850이었습니다.
> 최종 모델은 Validation으로만 골랐고, 그 선정 기록을 먼저 커밋한 다음 Test를 한 번만 봤습니다. Test는 E0 0.7188 → E2 0.9766(128장 중 125장)으로 25.78%p 올랐습니다. 녹병 Recall은 Val 기준 0.64 → 0.96입니다.
> 추가로 교과 9의 OpenCV 규칙도 실험했습니다. HSV로 잎과 병반 후보를 나눠 면적비를 냈는데 정상·병든 잎 차이가 작아 효과가 없었고, 대신 모델 확신도가 0.9 미만이면 "확인 필요"로 넘기는 규칙은 Test에서 14%를 보류하고 나머지 110장을 99.1% 정확도로 자동 처리했습니다.

**③ 서비스 성능 (40초)**
> 같은 Validation 이미지로 조건별 5번 측정한 중앙값입니다. 동기 첫 요청(MISS)은 22ms, 같은 이미지 재요청(HIT)은 1.4ms였습니다. HIT의 inference_ms가 null인 건 0초가 아니라 추론을 건너뛰었다는 뜻입니다. 비동기는 접수 응답이 10.6ms로 빨리 돌아오지만, 최종 결과 확인은 118ms로 오히려 늦었습니다. 0.1초 간격으로 상태를 조회하기 때문이고, 모델이 빨라진 게 아니라 접수와 추론을 분리한 효과입니다.

**④ 검증과 한계 (30초)**
> 기능 테스트 18개를 실제로 돌렸습니다. Worker를 끄면 작업이 queued로 남았다가 재시작하면 처리되고, Redis를 끄면 동기는 추론으로 계속 동작하고 비동기는 503과 failed 기록이 남습니다. 한계는 학습을 seed 하나로 한 번씩만 했고, Test가 128장이라 한 장이 0.78%p이며, 동시 요청 부하 시험은 하지 않았다는 점입니다.

## 3. 예상 질문과 답

**모델·학습**

- **Head-only와 Full Fine-tuning 차이는?** Head-only는 사전학습된 Backbone을 고정하고 새 3클래스 분류층만 학습합니다(`--freeze-backbone`). Full은 옵션을 빼서 Backbone까지 같이 조정합니다. 콩잎 반점 같은 세밀한 특징은 ImageNet 특징만으로 부족해서 Full이 크게 좋아졌습니다.
- **왜 Full은 학습률을 낮췄나?** (2e-4 → 5e-5) 사전학습 가중치를 크게 흔들면 이미 배운 특징이 망가지기 때문에 작은 학습률로 조금씩 조정했습니다.
- **과적합은 없나?** E2는 Train 1.0, Val 0.985, Test 0.977로 차이가 작습니다. Epoch마다 Val로 평가해 가장 좋은 Epoch(4)을 저장했습니다.
- **Test를 모델 선택에 쓰지 않았다는 근거는?** 선정 기준과 결과(`reports/data/model_selection.md`)를 Test 전에 커밋했고, Test를 실행할 때마다 `test_runs.log`에 기록이 남습니다. 커밋 순서로 확인할 수 있습니다.
- **Val 0.985인데 Test는 0.977로 낮은 이유?** 표본이 작아서입니다. Test 128장에서 한 장이 0.78%p라 3장 틀린 것과 2장 틀린 것 차이 정도입니다.
- **남은 오류는?** Test 3장이 모두 녹병(bean_rust)입니다. 초기 녹병 반점이 작고 옅어서 잎맥·반점병과 헷갈리는 것으로 봅니다.
- **제공 코드를 수정했나?** 학습·서비스 코드는 수정하지 않았습니다. 평가(`training/evaluate.py`), 데이터 준비, 성능 측정, 화면 캡처, 규칙 실험 스크립트만 따로 추가했습니다.
- **%p와 %는?** 0.7188 → 0.9766은 25.78%p 상승입니다. 비율 상승률(%)과 다릅니다.

**서비스 구조**

- **202는 무엇?** "접수됐다"이지 "끝났다"가 아닙니다. 결과는 `/api/async/jobs/{id}/`로 조회해서 `done`을 확인합니다.
- **동기와 비동기는 언제 쓰나?** 추론이 짧고 바로 결과가 필요하면 동기, 추론이 길거나 요청이 몰리면 비동기가 웹 서버를 붙잡지 않습니다. 이번 측정은 추론이 17ms로 짧아 동기가 더 빨랐고, 동시 요청 부하는 측정하지 않았습니다.
- **비동기 최종 시간이 왜 더 느린가?** 브라우저/스크립트가 0.1초 간격으로 상태를 조회하기 때문입니다. DB 기록상 Worker 처리 자체는 30~45ms입니다.
- **Redis를 세 군데 쓰는 이유?** DB 1 = 결과 캐시, DB 2 = Celery 작업 큐(브로커), DB 3 = Celery 결과 저장으로 용도를 나눴습니다.
- **캐시 키는?** `vision:classify:<모델경로 해시>:<이미지 SHA-256>`, TTL 600초. 같은 바이트의 이미지면 HIT, 모델을 바꾸면 키가 달라져 이전 모델 결과를 재사용하지 않습니다.
- **HIT인데 `inference_ms`가 null?** 추론을 안 했다는 뜻입니다. 0ms로 적으면 "아주 빠른 추론"으로 오해되기 때문에 null로 둡니다.
- **Redis가 죽으면?** 동기는 캐시 없이 추론해서 200으로 응답, 비동기는 큐에 못 넣으니 503을 주고 DB에 failed로 남깁니다. Redis 재시작 후 Worker가 자동 재연결했습니다(T-15).
- **Worker가 죽으면?** 작업은 queued로 큐에 남고, Worker를 다시 켜면 처리됩니다(T-10). 처리 중 파일이 없으면 failed + 오류 메시지가 DB에 남습니다(T-16).
- **왜 GPU가 아니라 CPU 추론?** 제공 코드가 `pipeline(device=-1)`로 CPU를 씁니다. GPU(RTX 3060)는 학습·평가에만 썼습니다.
- **첫 요청이 3~4초 걸린 이유?** FastAPI와 Worker가 각자 첫 요청 때 모델을 메모리에 올리기 때문입니다(워밍업). 성능 비교에서는 제외하고 따로 적었습니다.
- **Docker에 FastAPI도 넣지 않은 이유?** 평가 가이드 구조가 "FastAPI·Celery는 WSL 가상환경, Docker는 Redis·PostgreSQL만"이기 때문입니다. 처음엔 전부 Docker로 돌렸다가 가이드에 맞춰 다시 측정했고, 그 기록도 `docker_mode_02/`에 남겼습니다.

**OpenCV 개선 실험**

- **HSV 규칙이 왜 효과가 없었나?** 녹병 초기 반점은 작고 황록색이라 녹색 구간에 섞이고, 반대로 흙·그림자가 잎 가장자리에 들어오면 병반으로 잡힙니다. Train에서 병든 잎 중 정상 잎의 상위 5% 기준을 넘는 비율이 4.8%뿐이었습니다.
- **"확인 필요" 규칙은 결과를 바꾸나?** 라벨은 그대로 두고 사람이 볼 사진만 표시합니다. 모델 정확도(0.9766)와 시스템 지표(보류율 14.1%, 자동 통과분 정확도 0.9909)를 따로 보고했습니다.
- **기준값은 어떻게 정했나?** 면적비 기준은 Train, 점수 기준(0.9)은 Validation에서 정했고, 커밋한 뒤 Test에 한 번 적용했습니다.
- **Val 보류율 5%인데 Test는 14%?** Val 133장에서 정한 기준이라 데이터가 바뀌면 달라집니다. Test를 보고 기준을 다시 고치지 않았습니다.
- **다음에 한다면?** 잎만 남기는 ROI/GrabCut 마스크로 배경 영향 줄이기, Grad-CAM으로 녹병 오류에서 모델이 어디를 봤는지 확인, seed를 바꾼 반복 학습으로 편차 확인.

**진행 과정에서 고친 것 (물으면)**

- 처음에 다른 프로젝트 가상환경으로 학습 → 프로젝트 전용 `.venv`를 만들어 재학습·재측정 (같은 seed라 모델이 비트 단위로 동일)
- 처음 시연에 Test 이미지를 씀 → 측정·시연을 Validation으로 교체, Test는 최종 1회만
- `pytest -q`가 `No module named 'ai'` → `python -m pytest`로 실행 (4 passed)
